# NextLink schedule plan — data model

## เป้าหมาย

ระบบนี้ตอบคำถามเดียว: **วิชาเลือกแต่ละตัวควรสอนคาบไหน ห้องไหน**

โจทย์ไม่ใช่การเก็บตารางที่ตัดสินใจแล้ว แต่คือการหาตารางจากข้อจำกัดสองด้าน —
ช่วงที่บริษัทสอนได้ กับห้องที่ภาคใช้ได้ ข้อมูลจึงต้องเก็บ *ทางเลือก* ไม่ใช่
เฉพาะคำตอบ

## ความแตกต่างสำคัญจากรุ่นก่อน

รุ่นก่อนเก็บตารางเป็น `course_sessions` (วัน-เวลา-ห้องที่เจาะจงแล้ว) ซึ่งตอบได้
ว่า "วิชานี้สอนเมื่อไร" แต่ตอบไม่ได้ว่า "ย้ายไปไหนได้บ้าง" ระบบวางแผนต้องรู้
ทางเลือกทั้งหมด ข้อมูลจึงแยกเป็นสองส่วนที่ไม่ปนกัน:

| ส่วน | คืออะไร | ใครเป็นเจ้าของ |
| --- | --- | --- |
| `PlanCourse.availability` | ช่วงที่บริษัทแจ้งว่าสอนได้ | บริษัท — เป็นข้อเท็จจริง |
| `Assignment` | คาบและห้องที่ภาคเลือกให้ | ภาควิชา — เป็นการตัดสินใจ |

การแยกทำให้กด "จัดใหม่" แล้วโยน `Assignment` ทิ้งได้โดยข้อมูลบริษัทไม่แตะ และ
ทำให้ `localStorage` เก็บเฉพาะสิ่งที่คนตัดสินใจจริง ๆ

## คำศัพท์เวลา — `lib/slots.ts`

หน่วยพื้นฐานคือ **คาบ** (`SlotId` เช่น `"WED_AM"`) ไม่ใช่ช่วงเวลา เพราะบริษัท
สื่อสารด้วยคำว่า "พุธเช้า" ไม่ใช่ "09:00–12:00" การเก็บเป็นคาบทำให้เทียบ
ความสะดวกของบริษัทกับช่องในตารางเป็น array lookup ไม่ต้อง parse เวลาทุกครั้ง

- วัน: จันทร์–เสาร์ (6 วัน)
- คาบ: `AM` 09:00–12:00 · `PM` 13:00–16:00 · `EVE` 16:00–19:00
- รวม **18 คาบต่อห้องต่อสัปดาห์**

**คาบบ่ายกับคาบเย็นชนขอบกันที่ 16:00** ไม่มีช่วงพักคั่น การตรวจว่าเวลาทับกัน
จึงต้องใช้ช่วงแบบ half-open `[start, end)` เสมอ (`overlaps()` ใน `lib/slots.ts`)
ถ้าเขียนเป็นช่วงปิดท้าย วิชาบ่ายกับวิชาเย็นในห้องเดียวกันจะถูกมองว่าชนกันทุกคู่
มีเทสต์คุมข้อนี้ไว้ใน `scripts/check-scheduler.mjs`

`Assignment` เก็บ `startTime`/`endTime` จริงได้ (ค่าเริ่มต้นคือขอบของคาบ) โดย
**การวางและการแสดงผลใช้ระดับคาบ ส่วนการตรวจชนใช้เวลาจริง** วิชาที่สอน
12:00–15:00 กับ 09:00–12:30 อยู่คนละคาบแต่ชนกันจริง — ตรวจระดับคาบจะจับไม่ได้

## ห้องเรียน — `data/plan-rooms.json`

ห้อง 9 ห้อง แบ่งเป็นสองชั้น (`RoomTier`) ตามความยากในการขอใช้:

- `READY` — จุฬาพัฒน์ 6 ห้อง ภาคจัดลงได้ทันที
- `NEEDS_APPROVAL` — ตึก 3 / ตึก 4 ของคณะวิศวะ 3 ห้อง ต้องยื่นเรื่องก่อน

`seatsIsEstimated: true` หมายถึงตัวเลขที่นั่งมาจากวิชาที่เคยใช้ห้องนั้น จึงเป็น
*ขอบล่าง* ของความจุจริง ไม่ใช่ความจุที่ยืนยันแล้ว UI แสดงเป็น `~40 ที่นั่ง`
พร้อมไอคอน และ scheduler จะไม่จัดวิชาที่รับเกินตัวเลขนี้ลงห้องนั้น

**ประเภทห้องไม่ได้ถูกเก็บไว้** ทุกวิชาออกแบบให้นิสิตพกคอมมาเอง จึงไม่มีความ
ต่างระหว่างห้องบรรยายกับห้องปฏิบัติการในระบบนี้ ข้อจำกัดของห้องเหลือแค่จำนวน
ที่นั่งกับคาบที่ถูกกันไว้ (`blockedSlots`)

## ลำดับการเลือกห้อง

`planSchedule()` เรียก `autoAssign()` **สองรอบ** — รอบแรกเปิดเฉพาะห้อง `READY`
รอบที่สองเปิดห้องทั้งหมดให้เฉพาะวิชาที่รอบแรกจัดไม่ลง

ไม่ได้ทำเป็นคะแนน soft constraint เพราะคะแนนถูกกติกาอื่นโหวตแพ้ได้ — กฎ
"บริษัทเดียวกันได้วันเดียวกัน" อาจดันวิชาเข้าตึก 4 ทั้งที่จุฬาพัฒน์ยังว่าง แล้ว
จะอธิบายกับคนที่ต้องไปเดินเรื่องขอห้องไม่ได้ สองรอบให้การรับประกันแบบเด็ดขาด

## เทอมและปีการศึกษา

ระบบเก็บ **เทอมที่กำลังจัดหนึ่งเทอม** กับ **บันทึกของเทอมที่จบแล้ว** แยกกันคนละ
ชนิดข้อมูล ไม่ใช่ตารางเดียวที่มีคอลัมน์ `term`

| ส่วน | คืออะไร | แก้ได้ไหม |
| --- | --- | --- |
| `PlanCourse` + `Assignment` | เทอมที่กำลังจัด — ทางเลือกกับการตัดสินใจที่ยังขยับได้ | ได้ |
| `ArchivedTerm` + `ArchivedSession` | เทอมที่จบแล้ว — บันทึกว่าเกิดอะไรขึ้น | ไม่ได้ |

`ArchivedSession` ไม่ใช่ `Assignment` ที่ตั้ง `locked: true` เพราะทั้งสองตอบคนละ
คำถาม: assignment คือคำตอบที่ยัง "จัดใหม่" ทับได้ ส่วน session คือสิ่งที่ผ่านไปแล้ว
ถ้าใช้ type เดียวกัน scheduler กับ `usePlanState` จะรับข้อมูลของเทอมเก่าเข้าไปได้
โดยไม่มีอะไรกั้น และวันหนึ่งจะมีคนกด "จัดใหม่" แล้วเขียนทับประวัติ

**ห้องในบันทึกเก่าเก็บเป็นชื่อ (`roomName`) ไม่ใช่ `roomId`** ห้องถูกเปลี่ยนเลขหรือ
ยุบได้ ประวัติที่ชี้เข้า `data/plan-rooms.json` ของวันนี้จะมีสองอาการให้เลือกทั้งคู่
ผิด — ไม่ก็แสดงชื่อใหม่ทับของเดิม ไม่ก็ build พังในวันที่ห้องหายไปจากไฟล์ เก็บเป็น
ข้อความจึงเป็นการบอกว่า "ตอนนั้นเรียกห้องนี้ว่าอะไร" ซึ่งเป็นสิ่งที่บันทึกควรตอบ

`data/terms/index.json` เป็นรายชื่อเทอมทั้งหมด (รวมเทอมปัจจุบัน) และเป็นแหล่งเดียว
ของ label — ไฟล์ของแต่ละเทอมมี metadata ของตัวเองซ้ำไว้เพื่ออ่านไฟล์เดี่ยว ๆ ได้
`plan-data.ts` จะโยน error ถ้าสองที่ไม่ตรงกัน

การเพิ่มเทอมใหม่คือสามอย่าง: ไฟล์ `data/terms/<id>.json`, บรรทัดใน `index.json`
และ import ใน `ARCHIVE_FILES` (bundler ต้องเห็น path เป็น literal จึงสแกนโฟลเดอร์
ไม่ได้) — ลืมอย่างที่สาม `getArchivedTerms()` จะฟ้องชื่อเทอมที่ขาดไป

### สิ่งที่ตรวจตอนโหลด

นอกจากคาบที่ไม่รู้จัก บันทึกของแต่ละเทอมยังถูกตรวจว่า

- ทุก session ชี้ไปยังวิชาที่อยู่ในเทอมนั้นจริง
- คาบที่สอนอยู่ใน `availability` ที่บริษัทแจ้งไว้
- ห้องเดียวกันไม่ถูกใช้สองวิชาในคาบเดียวกัน
- จำนวนคาบที่สอนเท่ากับ `sessionsPerWeek` พอดี

เทอมที่จบแล้วไม่มีใครแก้ได้อีก ข้อผิดพลาดพวกนี้จึงไม่ใช่คำเตือนบนหน้าจอ แต่เป็น
error ตอน build ของไฟล์ข้อมูลเอง

## รายการห้อง — แก้ได้จากหน้าเว็บ

`data/plan-rooms.json` ไม่ใช่ความจริงสุดท้ายอีกต่อไป แต่เป็น **จุดตั้งต้นร่วมของภาค**
ภาคได้ห้องเพิ่มและเสียห้องระหว่างเทอม การรอแก้โค้ดหมายความว่าระบบผิดอยู่นานเท่ากับ
รอบการ deploy สิ่งที่คนแก้จึงวางซ้อนไว้ข้าง ๆ seed ไม่ใช่เขียนทับ (`lib/rooms.ts`):

| ส่วนของ `RoomEdits` | คืออะไร |
| --- | --- |
| `added` | ห้องที่คนเพิ่มเอง เป็นของคนนั้นทั้งก้อน |
| `overrides` | สิ่งที่แก้ *ทับ seed* ทีละฟิลด์ |
| `removed` | id ของห้อง seed ที่ถูกซ่อน |

แยกสามส่วนเพราะเจ้าของไม่เหมือนกัน: ถ้าไฟล์ seed อัปเดตในรุ่นถัดไป ห้องที่ไม่มีใคร
แตะจะได้ค่าใหม่ตามไฟล์ ส่วนห้องที่แก้ไว้ยังคงเฉพาะฟิลด์ที่แก้ และห้องที่ "ลบ" คือ
**ซ่อน** ไม่ใช่ลบจริง — กด "คืนค่าเริ่มต้น" แล้วรายการของภาคกลับมาครบ

**ลบห้องพร้อมทิ้งวิชาในห้องนั้น** `removeRoom` ลบห้องกับ assignment ในห้องนั้นใน
คอมมิตเดียว undo ครั้งเดียวจึงคืนได้ทั้งคู่ ถ้าปล่อย assignment ไว้ มันจะชี้ไปยัง
ห้องที่ไม่มีอยู่ — หายจากกระดานแต่ยังถูกนับใน KPI ซึ่งแย่กว่าทั้งสองทาง

**id ของห้องเป็น ASCII** เพราะมันคือ URL (`/rooms/<id>`) ชื่อห้องไทยจะกลายเป็น
percent-escape ยาวเหยียดเวลาแปะในแชท ระบบจึงดึงเฉพาะส่วน ASCII ของชื่อ (เลขห้อง)
มาใช้ และกันชนกับ id ของห้องที่ถูกซ่อนอยู่ด้วย — ห้องที่ซ่อนกลับมาได้เสมอ

### การจองคาบให้วิชาบังคับ

`PlanRoom.blockedSlots` มีมาตั้งแต่ต้นแต่แก้ผ่านหน้าจอไม่ได้ ตอนนี้แก้ได้จากช่องใน
กระดานและในตารางของห้อง โดย **ยังเป็นฟิลด์เดิม** ไม่ใช่ชนิดใหม่ที่ตั้งชื่อว่า "โน้ต"

เพราะการกันคาบต้อง *มีผล*: scheduler ข้ามคาบนั้น (`ROOM_BLOCKED`) และกระดานไม่รับ
การลากมาวาง โน้ตที่ไม่กันคาบคือโน้ตที่จะถูกจัดตารางทับในรอบถัดไป ส่วน `reason`
บังคับให้พิมพ์ เพราะคาบที่ถูกกันโดยไม่บอกเหตุผลคือคาบที่ไม่มีใครกล้าปลด

## เช็กลิสต์งานเอกสาร — `lib/checklist.ts`

จัดตารางเสร็จยังไม่ใช่จบงาน ยังมีจดหมายเชิญ จดหมายแจ้งชั่วโมงสอน และการดึงคน
สี่กลุ่มเข้า MCV ที่ต้องทำก่อนสัปดาห์แรก รายการนี้เคยอยู่ในสเปรดชีตข้าง ๆ ระบบ
ซึ่งเป็นสาเหตุที่วิชาถูกจัดลงตารางเรียบร้อยแต่ไม่มีอาจารย์ที่เปิดหน้าวิชาใน MCV ได้

**คำตอบมีสองชนิด เพราะคำถามเป็นคนละชนิด**

| ชนิด | ใช้กับ | ค่า |
| --- | --- | --- |
| `ReceiptStatus` | จดหมายสองฉบับ | `NOT_RECEIVED` · `IN_PROGRESS` · `RECEIVED` |
| `DoneStatus` | งานใน MCV สี่ข้อ | `NOT_DONE` · `DONE` |

จดหมายเป็นสิ่งที่ *รอจากคนอื่น* จึงมีสถานะกลางที่แปลว่า "ส่งเรื่องแล้วยังไม่กลับมา"
ส่วนงานใน MCV เจ้าหน้าที่ทำเอง — "กำลังดำเนินการ" ของงานแบบนั้นแปลได้แค่ว่าเปิดแท็บ
ค้างไว้ ส่วนรหัส Join เป็นข้อความ และนับว่าเสร็จเมื่อมีตัวอักษรจริง (เว้นวรรคล้วน
ไม่นับ) เพราะรหัสว่างคือรหัสที่ยังให้นิสิตไม่ได้

**เก็บเฉพาะช่องที่มีคนตอบ** `checklists` เป็น `Record<courseId, Partial<CourseChecklist>>`
วิชาที่ยังไม่มีใครแตะจึงไม่กินที่ใน storage เลย และ `readChecklist()` เป็นด่านเดียว
ที่เติมค่าเริ่มต้น — ค่าที่อ่านไม่ออก ผิดชนิด หรือมาจากรุ่นก่อนจะกลายเป็น "ยังไม่เสร็จ"
เสมอ ทิศทางนี้เลือกไว้ตั้งใจ: ต้นทุนของการแสดงงานที่ยังไม่ทำว่าทำแล้ว คือไม่มีใครทำ

**เช็กลิสต์ผูกกับเทอมที่กำลังจัด** เทอมที่ปิดไปแล้วไม่มีปุ่มสลับให้กด — งานเอกสาร
ของเทอมที่จบแล้วไม่มีอะไรให้ติ๊กต่อ และแบบฟอร์มที่บันทึกคำตอบเรื่องเทอมที่ไม่มีใคร
ทำอะไรกับมันได้แล้ว คือแบบฟอร์มที่หลอกคนกรอก

`CHECKLIST_FIELDS` เป็นแหล่งเดียวของลำดับและชื่อช่อง ทั้งหัวตาราง คอลัมน์ใน Excel
และการนับ "ครบหรือยัง" อ่านจากลิสต์นี้ — มีเทสต์คุมว่าลิสต์ต้องครอบคลุมทุกฟิลด์ของ
`CourseChecklist` พอดี ไม่ขาดไม่เกิน

## ที่เก็บข้อมูล

- `data/plan-courses.json`, `data/plan-rooms.json` — ข้อมูลตั้งต้นของเทอมที่กำลังจัด
  bundled กับแอป
- `data/terms/index.json` + `data/terms/<id>.json` — รายชื่อเทอม และบันทึกของเทอม
  ที่จบแล้ว หนึ่งไฟล์ต่อหนึ่งเทอม
- `lib/plan-data.ts` — จุดเดียวที่รู้ว่าข้อมูลมาจากไหน ตรวจ `SlotId` ที่ไม่รู้จัก
  ตั้งแต่ตอนโหลด (typo อย่าง `"WED_MORNING"` จะไม่เงียบไปโผล่เป็นวิชาที่หายไป
  จากตาราง)
- `localStorage` คีย์ `nextlink.plan.v1` (`version: 2`) — เก็บสี่อย่าง:
  `assignments`, ฟิลด์ของวิชาที่คนแก้เอง, `roomEdits` (ห้องที่เพิ่ม/แก้/ลบ) และ
  `checklists` (งานเอกสารต่อวิชา)
  conflict กับรายการที่จัดไม่ได้คำนวณใหม่ทุกครั้ง ไม่เก็บ · ของเดิม `version: 1`
  ยังอ่านได้ ไม่ถูกล้างทิ้ง (แค่ไม่มีส่วนของห้อง)

ถ้าย้ายไป PostgreSQL ในอนาคต แก้แค่ `lib/plan-data.ts` — ส่วนที่อยู่เหนือขึ้นไป
รับ `PlanPayload` และไม่มีความเห็นเรื่องแหล่งข้อมูล สคีมาเดิมของรุ่นก่อนเก็บไว้ที่
[`docs/legacy/schema.prisma`](./legacy/schema.prisma)

## Data quality rules

- ห้ามใช้ `-`, ช่องว่าง หรือข้อความกำกวมแทนค่าที่ไม่ทราบ ใช้ nullable
- ห้ามใช้ email / LINE จริงในข้อมูลตัวอย่าง
- `availability` ต้องมีจำนวนคาบไม่น้อยกว่า `sessionsPerWeek` — `plan-data.ts`
  โยน error ถ้าไม่ครบ
- ความจุห้องที่ยังไม่ยืนยันต้องตั้ง `seatsIsEstimated: true` เสมอ อย่าปัดเป็น
  ตัวเลขที่ดูแน่นอน
